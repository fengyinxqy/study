# Egg.js 学习完整对话记录

**时间**：2026-04-24  
**学习者**：2 年 Vue 前端经验，Node.js/Egg 零基础  
**教学方式**：苏格拉底式提问法

## 一、为什么需要 Egg.js？

### 问 1：Node.js 原生 HTTP 服务的问题

**师**：你在前端调用后端 API 时，后端一定是一个 HTTP 服务。Node.js 本身有 `http` 模块可以创建服务器。但大家为什么不直接用原生 Node.js，而是选择 Express/Koa/Egg 这样的框架？

**生**：用框架的话，有一些封装好的轮子，能够开箱即用，不需要自己再去重复实现。提高开发效率。

**师**：没错。那深入一点 —— Node.js 原生处理请求时，你需要自己解析 URL 路径、解析请求体（JSON / 表单）、做路由分发。你觉得这些工作中，**最难"通用化"的是哪一部分？**

**生**：最难的是解析请求体和路由分发吧。可能有各种各样的请求体，很难一次性考虑到所有情况。路由分发也是，有各种各样的格式。他们底层将这些都处理好，相当于做了中间件。

**师**：对，中间件就是这类框架的核心抽象 —— 把你的请求处理逻辑拆成一个个小函数，管道式地传递。

## 二、Egg.js 的定位

### 问 2：企业级框架意味着什么？

**师**：Egg.js 是阿里开源的 Node.js 框架，它**基于 Koa 构建**。但 Egg 的定位是"企业级框架"。你觉得"企业级"这个词意味着什么？如果一个团队有 10 个人、代码量几万行、要维护两三年，和一个 2 个人的个人项目相比，这个场景下你会希望框架额外提供什么？

**生**：稳定、高效。

**师**：这两个词很准确，但太宽泛了。更具体地说：10 个人同时写后端代码，没有框架约束，会出现什么问题？

**生**：开发规则约束，有统一的约定。

**师**：完全正确 —— 这就是 Egg.js 最核心的理念：**约定优于配置（Convention over Configuration）**。

Egg.js 基于 Koa，但它给项目结构规定了强制的目录约定：

| 目录 | 用途 |
|------|------|
| `app/controller/` | 处理 HTTP 请求逻辑 |
| `app/service/` | 业务逻辑 |
| `app/middleware/` | 中间件 |
| `app/router.js` | 路由定义 |

10 个人写出来的项目，目录结构基本一样，新成员接手一看就懂。

## 三、洋葱模型中间件

### 问 3：中间件的执行顺序

**师**：Egg 继承 Koa 的中间件模型，也叫"洋葱模型"。一个请求进来，穿过一层层中间件到达路由，路由处理完后，响应再反向穿回去。

**问题：中间件里 `await next()` 前面和后面的代码，分别执行在什么时机？**

```js
async function middleware(ctx, next) {
  console.log('request in');
  await next();
  console.log('response out');
}
```

**生**：进入中间件时；下一个中间件执行完后。

**师**：完全正确：
- `await next()` 之前：请求进来时执行
- `await next()` 之后：路由处理完毕，响应回去时执行

这就是洋葱模型。

## 四、上下文 (Context)

### 问 4：ctx 是什么

**师**：在 Egg 中，每个请求处理函数都接收 `ctx` 参数：

```js
async ctx => {
  ctx.body = 'Hello';
}
```

`ctx.body = 'Hello'` 和原生 Node.js 的 `res.write('Hello')` 有什么区别？Egg 为什么把 `req` 和 `res` 封装到 `ctx` 里？

**生**：ctx 是 context 上下文。ctx.body 本质跟 res.write 一样。封装进去后更方便调用，减少函数传参。

**师**：对。Egg 的 `ctx` 是对 `req` 和 `res` 的代理，还混入了很多便捷方法（`ctx.query`、`ctx.params`、`ctx.throw`），不用来回切换 `req.xxx` 和 `res.xxx`。

## 五、Controller 和 Service 的分工

### 问 5：分层设计

**师**：Egg 强制把代码分成两层 —— `controller/` 处理 HTTP 请求，`service/` 处理业务逻辑。一个用户登录的请求，验证密码、查数据库、生成 token 这些操作，哪些该放 Controller，哪些该放 Service？

**生**：请求放在 controller，其他的放在 service。都写在 controller 太臃肿了，应该是各司其职，分层的。

### 问 6：Service 的生命周期

**师**：同一个 Service 方法，能不能被多个 Controller 调用？如果能，这说明 Service 和 Controller 的生命周期有什么不同？

**生**：能支持，`ctx.service.UserService.findUserById` 就行。说明 service 是全局互通的？

**师**："互通"是对的，但有一个重要细节：
- **Controller 是请求级的** —— 每个请求创建实例，请求结束就被回收
- **Service 是应用级单例** —— 整个应用启动时只创建一次，所有请求共用同一个 Service

**问题：如果一个 Service 里保存了一个变量 `this.name = 'Alice'`，两个不同用户同时请求时，这个变量会共享吗？**

**生**：Bob（后被覆盖）。

**师**：完全正确 —— B 把 A 的数据覆盖了。所以关键结论是：**Service 里绝对不能存请求相关的数据**（当前用户 ID、用户信息等），这些应该作为参数传递，或者存在 `ctx` 里。

## 六、路由参数

### 问 7：路径参数 vs Query 参数

**师**：Egg 路由定义在 `app/router.js` 中：

```js
router.get('/api/users/:id', controller.user.detail);
```

`:id` 是什么？Controller 中怎么获取？

**生**：`:id` 其实就是路由后跟随的参数。从 query 获取。

**师**：这里有个重要区别：
- **路径参数**：`/api/users/123` —— `:id` 在 URL 路径里，用 `ctx.params.id` 获取
- **Query 参数**：`/api/users?page=1` —— 在 `?` 后面，用 `ctx.query.page` 获取

**问题：获取用户详情，用 `/api/users/:id` 和 `/api/users?id=123`，哪种更 RESTful？**

**生**：第一种更好，更符合 restful 的资源路径格式。

## 七、多环境配置

### 问 8：配置的合并策略

**师**：Egg 支持多环境配置：`config.default.js`、`config.prod.js`、`config.local.js`。如果 `default.js` 和 `prod.js` 都定义了同一个配置项，Egg 怎么处理？

**生**：是先加载环境变量的，最后再试 default 的，会进行合并。

**师**：顺序上反了 —— 实际是**先加载 `default.js`，再加载对应环境的配置做合并覆盖**。比如：
1. 先加载 default → `{ port: 7001, dbHost: 'localhost' }`
2. 再加载 prod → `{ dbHost: 'prod-db.example.com' }`
3. 合并 → `{ port: 7001, dbHost: 'prod-db.example.com' }`

**问题：这种设计有什么意义？**

**生**：意义是，在各环境使用自己的配置，共用的写到 default，更清晰？

**师**：对 —— 共用基础配置 + 环境差异化覆盖。

## 八、自动加载与注入

### 问 9：为什么不需要 require？

**师**：在 Controller 里直接写 `this.service.user` 就能调用，但并没有 `require` 或 `import`。Egg 底层做了什么？

**生**：底层进行了注入，将这些注入到了上下文中。

**师**：对。Egg 启动时自动扫描 `app/service/`、`app/controller/`、`app/middleware/` 目录，按约定把文件挂载到 `ctx` 或 `app` 上，所以不需要手动 require。

## 九、全局错误处理

### 问 10：如何区分业务错误和系统错误？

**师**：如果 Service 里 `throw new Error('xxx')`，你觉得会直接暴露给前端吗？错误中间件应该放在洋葱模型的哪一层？

**生**：会暴露给前端，应该在靠近路由的中间件。

**师**：这里要纠正两点：
1. **Egg 默认不会把错误直接暴露给前端** —— 生产环境返回通用 500
2. **错误中间件应该放在最外层**（最先定义的中间件），这样它包住所有后续中间件和路由

**问题：在业务代码中，怎么告诉错误处理中间件"这是 400 参数错误，不是 500 系统错误"？**

**生**：（思考后）不知道。

**师**：`ctx.throw(400, '用户名不能为空')` 本质上是往错误对象上加了 `status` 属性：

```js
const err = new Error('用户名不能为空');
err.status = 400;
throw err;
```

外层 catch 通过 `err.status` 判断：
- 有 status 且 < 500 → 业务错误，直接返回
- 没有 status 或 >= 500 → 系统错误，返回通用 500

```js
try {
  await next();
} catch (err) {
  const status = err.status || 500;
  ctx.status = status;
  ctx.body = { message: err.message };
}
```

## 十、插件机制

### 问 11：插件 vs 直接 require

**师**：Egg 的很多功能通过插件提供，比如数据库连接需要安装 `egg-sequelize`，然后在 `plugin.js` 中启用：

```js
exports.sequelize = {
  enable: true,
  package: 'egg-sequelize',
};
```

这种插件机制和直接 `require` 一个 npm 包相比，优势是什么？

**生**：require 的话，关闭需要进行代码移除，插件机制关闭就行。并且不需要考虑顺序问题。

**师**：对：
- **开关控制**：`enable: true/false` 一行搞定
- **无需改代码**：不需要到处 require/import
- **生命周期管理**：Egg 统一管理插件的加载顺序和初始化
